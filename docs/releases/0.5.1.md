# ConfigOps 0.5.1

Released 2026-08-24. This maintenance release lets authorized tools inspect ConfigOps evidence, validate restore eligibility, and—only with separate authority plus an explicit danger acknowledgement—undo one mutation without gaining a generic settings writer.

## Agent-readable operations

- Nine site-scoped native WordPress Abilities expose state, capture discovery, bounded mutation evidence, named Change Session control, read-only restore planning, and explicitly authorized single-mutation undo.
- Machine-readable JSON `wp configops` commands execute the same application services with explicit WordPress capability checks.
- Agent responses use schema version 2, immutable site scope, bounded inputs, behavioral annotations, and machine-readable failure codes; clients can discover apply authority and its required confirmation explicitly.
- Restore planning runs the real site, active-capture, reference, filtered-read, autoload, current-state, adapter, and verified-key checks without changing WordPress state.
- `configops/apply-restore` requires `configops_apply` plus `dangerouslyRunUndo: true`; WP-CLI exposes the same contract as `restore apply --mutation=<id> --dangerously-run-undo`.
- The danger acknowledgement replaces human confirmation only. Apply repeats the plan and ordinary restore checks, then retains locking, append-first audit, verification, and compensation.

## Compatibility fixes

- WP-CLI observations no longer disappear when the optional global `--user` argument is omitted; shell-authorized commands record actor ID `0`.
- Site and network undo refuse the write when a `pre_*` filter or path-relevant missing-row default virtualizes the target. Normal post-read transforms such as Yoast's `option_wpseo` remain conflict-checked instead of being refused solely because a hook is registered.
- Large-network activation avoids a synchronous all-site loop. Existing sites provision idempotently when they next load ConfigOps.
- Plugins without a dedicated adapter retain their source owner and capture-time version when WordPress can resolve it. Their nested leaf keys are readable in review while remaining explicitly unmapped and semantically untrusted.
- Settings API options now distinguish the plugin or theme that registered them from WordPress Core performing the final option write. Direct callers keep precedence, and the provenance improvement does not grant adapter semantics or broader undo.

## Plugin contracts

- Adds a WooCommerce core adapter for the WordPress.org-visible 10.3, 10.7, 10.9, and 11.0 lines. It explains core settings, performance controls, feature flags, Point of Sale receipt details, email settings, and bundled offline gateways.
- Keeps HPOS datastore changes and Cost of Goods content switches visible but non-restorable because reversing one option cannot reverse their data changes.
- Each real-plugin version job now audits the release’s option map, registered defaults, or Settings API and fails when an exposed setting still has no tested adapter meaning.

## Automation authorization boundary

Agent clients can read evidence, control named Change Sessions when granted that capability, and validate a proposed restore. Human confirmation remains the default. Operators may grant `configops_apply` to a service user that is allowed to replace it, but each mutation still requires the explicit danger acknowledgement. ConfigOps 0.5.1 does not expose generic option writes, raw SQL, plugin installation, session-wide agent undo, or network-wide agent undo.

## Release evidence

- Complete plugin build, UI budget, runtime policy, PHP parser, unit, adversarial, WordPress integration, WP-CLI, Multisite, exact-adapter, and published-settings-surface gates.
- Desktop and mobile documentation plus site and Network Admin browser checks.
- Deterministic release metadata and WordPress.org payload validation.
